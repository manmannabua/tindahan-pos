# Sync Protocol

The sync protocol moves data between each terminal's IndexedDB and PostgreSQL. It has two
independent directions:

```
            PUSH (device → server)                    PULL (server → device)
  local outbox ──► POST /api/v1/sync/push     GET /api/v1/sync/pull?cursor=… ──► Dexie tables
  "things that happened here"                 "things that changed centrally"
```

Guarantees:

1. **Exactly-once effect** for every pushed operation, no matter how many times it is sent.
2. **No lost operations** — an operation leaves the outbox only after the server acknowledges it.
3. **No lost changes on pull** — the cursor never skips a row, even with concurrent writers.
4. **Financial facts are never discarded** — a sale that happened is recorded even if it makes
   stock negative or totals disagree; the anomaly is flagged instead.

---

## 1. Identity

| ID | Generated by | Purpose |
|---|---|---|
| `device_id` | server at registration | which terminal |
| `operation_id` | device, UUIDv7, per outbox row | idempotency key of the *delivery* |
| `entity_id` (`sale_id`, `payment_id`, …) | device, UUIDv7 | primary key of the record in PostgreSQL |

Both levels exist on purpose:
- `operation_id` makes retries of the *same message* safe.
- `entity_id` as the primary key makes even a *re-created message* for the same sale safe
  (e.g. if the outbox row was rebuilt after a local DB repair).

## 2. Local outbox

Dexie table `outbox`:

| Field | Meaning |
|---|---|
| `seq` | auto-increment, local order |
| `operationId` | UUIDv7, unique |
| `deviceId` | |
| `entityType` | `cash_session`, `sale`, `cash_movement`, `stock_count`, … |
| `entityId` | UUID of the record |
| `operation` | `cash_session.open`, `sale.complete`, `sale.void`, `cash_movement.record`, … |
| `payload` | complete JSON body, frozen at creation time |
| `priority` | lower = sent first (table below) |
| `createdAt` | device time |
| `attemptCount`, `lastAttemptAt`, `nextAttemptAt` | retry bookkeeping |
| `status` | `PENDING` → `SYNCING` → `SYNCED` \| `FAILED` \| `CONFLICT` |
| `error` | last error `{code, message}` |

The outbox row is written **in the same Dexie transaction** as the business records. A sale
without an outbox row (or vice versa) is therefore impossible.

`SYNCED` rows are kept for 7 days (for the sync monitor UI) and then pruned. The business
records themselves (`sales`, …) are kept locally for receipt reprinting per a retention setting.

### Priority

| Priority | Operations | Why this order |
|---|---|---|
| 5 | `cash_session.open` | sales reference their cash session (dependency first) |
| 8 | `customer.upsert` | a sale may reference a customer created offline (dependency first) |
| 10 | `sale.complete` (includes items **and** payments) | revenue first; payments are part of the sale aggregate so a sale is never half-synced |
| 15 | `sale.void` | voids happen minutes after the sale, before the shift closes |
| 20 | `payment.*` recorded after the sale (future: layaway, credit collection) | |
| 30 | `inventory.*` (adjustments, counts done offline) | |
| 40 | `cash_movement.record`, `cash_session.close` | |
| 50 | `return.create` | |
| 60 | everything else | |

Priorities only optimize the common case. Correctness never depends on arrival order: a
missing dependency returns `DEFERRED`, and time-based rules compare business timestamps
(e.g. a void is valid if it *occurred* before the shift closed, even if it syncs after the
close operation).

After push completes: **pull** server changes, then **reconcile** inventory (see §5).

> Why are payments inside `sale.complete` instead of separate operations? A sale and its
> payments must be committed atomically — a sale that exists on the server without its
> payments would show as unpaid in reports. Keeping them in one operation makes that
> impossible. Separate `payment.*` operations exist only for payments made *after* a sale.

## 3. Push

### Request

```http
POST /api/v1/sync/push
Authorization: Bearer <user access token bound to device>   (or device token for background)
X-Device-Id: <device_id>

{
  "device_id": "…",
  "operations": [
    {
      "operation_id": "0192…",
      "entity_type": "sale",
      "entity_id": "0192…",
      "operation": "sale.complete",
      "created_at": "2026-09-26T03:15:00Z",
      "payload": { … }
    }
  ]
}
```

Batch size ≤ 100 operations. The client sends them in `(priority, seq)` order.

### Server processing

For each operation, **in order, each in its own transaction**:

```
BEGIN
  INSERT INTO sync_operations (id, …) VALUES (:operation_id, …)
    ON CONFLICT (id) DO NOTHING RETURNING id
  if no row returned:                           -- seen before
      ROLLBACK; return stored result (status = DUPLICATE)
  handler = HANDLERS[operation]                 -- e.g. SaleSyncHandler
  result  = handler.apply(payload)              -- INSERT sale (PK = entity_id), items, payments,
                                                --   inventory movements, balances, review flags
  UPDATE sync_operations SET status='APPLIED', result=:result
COMMIT
```

Why this is safe under concurrency: if the same operation arrives twice at the same time (a
retry fired while the first request is still running), the second `INSERT … ON CONFLICT`
blocks on the first transaction's uncommitted row. When the first commits, the second sees
the conflict and returns `DUPLICATE`. If the first rolls back, the second proceeds. No Redis
lock is needed — PostgreSQL's unique index is the lock.

Handlers also check the entity itself: if `sales.id` already exists (new `operation_id`, same
sale) the handler compares a payload hash — equal → `DUPLICATE`, different → `CONFLICT`.

### Per-operation results

```json
{
  "results": [
    { "operation_id": "…", "status": "APPLIED",   "server_version": 123 },
    { "operation_id": "…", "status": "DUPLICATE" },
    { "operation_id": "…", "status": "DEFERRED",  "error": {"code": "sync.dependency_missing"} },
    { "operation_id": "…", "status": "REJECTED",  "error": {"code": "validation_error", …} },
    { "operation_id": "…", "status": "CONFLICT",  "error": {"code": "sync.payload_mismatch"} }
  ],
  "server_time": "…"
}
```

| Server status | Client action |
|---|---|
| `APPLIED`, `DUPLICATE` | mark `SYNCED` (both are successful acknowledgments) |
| `DEFERRED` | keep `PENDING`, retry later; does not count as a failure (dependency not there yet) |
| `REJECTED` | mark `FAILED`; shown in sync monitor for a manager; never auto-retried |
| `CONFLICT` | mark `CONFLICT`; shown in sync monitor; requires a decision |
| HTTP 5xx / network error | whole batch stays `PENDING`, exponential backoff (2s → 5 min, jitter) |
| HTTP 401 | refresh token / device token, retry |

A `REJECTED` operation must be rare. For sales, business-rule problems (negative stock,
deactivated product, price mismatch, cashier since deactivated) are **not** rejections: the
sale is stored and a `review_flag` is raised. Rejection is for malformed payloads or
tenant/device violations (a device pushing data for another company).

### Crash-safety on the client

1. Row set to `SYNCING` before sending (so the UI can show progress).
2. On app start, any `SYNCING` rows are reset to `PENDING` — the previous attempt's outcome is
   unknown, and resending is safe because of idempotency.
3. Only after a successful response is a row set to `SYNCED`.

## 4. Pull

Terminals download master data (products, barcodes, prices, units, categories, tax rates,
payment methods, staff, settings) and their branch's inventory balances.

```http
GET /api/v1/sync/pull?cursor=<opaque>&limit=1000
→ {
    "changes": { "products": [...], "barcodes": [...], "prices": [...], ... },
    "next_cursor": "…",
    "has_more": true
  }
```

### The cursor problem and the `sync_txid` solution

The naive approach — "give me rows with `updated_at > last_seen`" — loses data: transaction A
starts and stamps a row at 10:00:00, transaction B stamps at 10:00:01 and commits first, the
device pulls (cursor → 10:00:01), then A commits. A's row has a *lower* timestamp than the
cursor and is never pulled.

Solution used here:

- Every syncable table has `sync_txid BIGINT`, set by a trigger to
  `pg_current_xact_id()` on insert/update (the writing transaction's ID).
- A pass fixes `hi = pg_snapshot_xmin(pg_current_snapshot())` when it starts and returns rows
  with `lo <= sync_txid < hi` — i.e. rows written by transactions that are **older than every
  still-running transaction**. Anything newer waits for the next pass, which starts at `lo = hi`.
- The window is half-open `[lo, hi)`: on an idle database the horizon equals the *next*
  transaction id, so the next write receives exactly `hi` (an early version used `(lo, hi]` and
  missed such rows — caught by `tests/committed/test_sync_pull.py`).
- Within a pass, pages continue with a keyset cursor `(sync_txid, primary key)` table by table.
- A long-running transaction holds the horizon back; pulls then return nothing newer until it
  finishes (keep transactions short).

This guarantees that once the cursor passes a transaction ID, no transaction with a lower ID
can still commit. It is the same technique used by logical-replication-style sync engines.

Deletions are soft (`is_active = false`), so they arrive as ordinary updates.

### Initial download

Device initialization is a full pull from cursor 0, written in batches with `bulkPut`, with a
progress count per table (see [DEVICE_MANAGEMENT.md](DEVICE_MANAGEMENT.md)). The cursor is
stored only after a batch is written, so an interrupted download resumes where it stopped.

## 5. Inventory reconciliation

The local `inventory` table = last server snapshot + local provisional movements not yet
confirmed. After a pull delivers new `inventory_balances` rows, the device:

1. Replaces its snapshot quantity with the server's.
2. Drops local provisional movements whose `referenceId` (sale id) is already synced
   (the server balance now includes them).
3. Re-applies provisional movements that are still pending.

Result: local stock = server truth + my unsynced sales. See
[INVENTORY_LEDGER.md](INVENTORY_LEDGER.md#multi-terminal-offline-conflict).

---

## 6. Conflict policy

| Data | Direction | Policy |
|---|---|---|
| Sales, payments, cash movements, returns | device → server | Append-only facts. Never overwritten. Duplicates collapse via PK. |
| Inventory quantity | derived | Ledger sums; negative results flagged, never "corrected" silently. |
| Master data (products, prices) | server → device | Server wins. Devices do not edit master data offline. |
| Customers created offline | device → server | Insert with client UUID; if a matching phone already exists, both kept and flagged for merge. |
| Void of a sale created on another device | device → server | Allowed online only (needs the original sale on the server). |

## 7. Status shown to the cashier

`ONLINE` · `OFFLINE` · `SYNCING — 24 pending` · `SYNC ERROR` · `Last synced: 2 minutes ago`

Derived from: connectivity monitor (heartbeat `GET /api/v1/health` every 15 s while visible,
plus `online`/`offline` browser events — the browser event alone is unreliable), outbox counts
(Dexie `liveQuery`), and `meta.lastSyncAt`.

Sync runs on a timer (every 10 s when online and the outbox is non-empty, 60 s otherwise), on
reconnect, and after each completed sale. It never blocks the UI thread with long work; large
pulls are written in chunks.
